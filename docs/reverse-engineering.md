# 逆向分析与验证记录

分析对象为用户提供的 CHSI Android App 2.6.1，记录日期为 2026 年 10 月 21 日。目标是理解 `chesicc://idphoto/...` 的处理方式，并判断独立客户端能否把预先拍摄的 JPEG 送入同一采集任务。

本次恢复了三份运行时 DEX、与该流程相关的 Java 代码和 832 个选定字符串 ID 的返回值，并据此实现了独立上传客户端。随后，一张用户提供的预拍 JPEG 完成真实上传，后台返回 `qualityStatus=PASS`。这项结果针对当次任务和那张照片；它不表示所有照片、所有任务或后续报名审核都会通过。

本公开仓库记录分析方法与协议，不发布原 APK、DEX、完整反编译源码、原始进程内存、真实二维码、JWT、OSS 临时凭证、照片、照片摘要或实际 ETag。文中的类名和字段名用于说明证据位置。

## 1. 静态 JADX 为什么只能看到壳

最初使用 JADX 1.5.6 直接导入 APK。Manifest 可以确认 `CaptureIdPhotoActivity` 导出，并接受 scheme 为 `chesicc`、host 为 `idphoto` 的 `VIEW` Intent，但最初可读 DEX 只有四个壳类，没有目标 Activity 的业务实现。

`StubApp.attachBaseContext()` 根据 ABI 提取并加载 `libjgcccc*.so`，再经 native 接口初始化原始 Application。包内的 `qh` 容器头、Jiagu 标记、加载器字符串及配置共同指向 Qihoo／360 Jiagu 加固。

壳 DEX 的数据区结束位置之后还有约 4.99 MB 附加载荷。对可打印配置记录做有边界的解码，恢复出 67 条元数据，包括原始 Application、包名、入口 Activity 和壳自身的版本字段。这一步只解释了配置记录，没有得到业务 DEX，也没有建立整个容器的通用解密算法。

后来从运行目录取得的 `.jiagu/classes.dex` 与 APK 附加载荷逐字节相同，仅少末尾三个零字节。它是保护容器的落地副本，因此系统 `dex2oat` 报它不是有效 ZIP／DEX，不能单凭这条日志判断业务 DEX 尚未加载。

进一步检查可确定该容器包含配置段及三个有长度前缀的保护块：配置段之后的数量字段为三，三个块的边界恰好覆盖运行时落地文件。长度字段、偏移和文件比较结果保存在 [容器布局元数据](../analysis/container-layout.json)。它们仍不是普通 DEX；容器分段识别与运行时明文提取是两项不同成果。

## 2. 在隔离模拟器中读取已加载 DEX

运行环境采用独立的、可 root 的 Android 7.0／API 24 AOSP x86_64 模拟器。动态分析阶段隔离网络，没有使用真实二维码或提交照片。ADB 操作显式选择该模拟器，并校验 QEMU 标记、目标包名和 PID。

先尝试 Frida 17.24.3 的加载器观察与内存扫描。早期尝试只得到原壳 DEX，进程很快结束。随后不注入 Frida 的正常启动对照也出现启动异常，因此没有把退出现象直接归因为某一种反调试机制。

关键进展来自不注入进程的后备路径：在 root ADB 下保存目标进程的内存映射，通过 `/proc/<pid>/mem` 读取可读的匿名及应用相关映射，再在主机上搜索 DEX 头和结构特征。候选文件要经过长度、表偏移和边界检查，随后按内容去重。

最终取得三份包含业务类的 DEX，其中一份实际声明了 `CaptureIdPhotoActivity`。为交给工具分析，只重算了 DEX 头部的 SHA-1／Adler-32 校验字段；处理前后从偏移 32 起的内容保持相同。没有通过这一步修改业务指令、伪造方法返回值或恢复 native 方法体。

这应称为取得了可分析的运行时 DEX，不能称为“完全解壳”。JADX 全量反编译仍报告 38 个方法错误；部分代码继续表现为 native 方法或受保护调用。

## 3. 补回字符串，同时保留 native 边界

业务代码中的大量常量被替换成 `StubApp.getString2(int)`。仅有类名和方法结构，还不足以确认 URL、字段名和状态码。

改用 Frida 16.7.19 的短脚本，在启动后的短窗口中调用已加载的字符串解码入口。首轮取得 789 个选定 ID 的返回值；之后分别补解 57 项和 12 项，合并后得到 832 个不同 ID。各轮有重叠，因此不是三轮数量的简单相加。

首轮 RPC 没有报错，但其中两个关键 URL 返回了乱码或空串。独立补解后，才确认它们分别是 `/idphoto/v1/check` 和 `/idphoto/v1/capture/checkst`。合并过程保留原始结果与冲突记录，并用补解值建立阅读副本；没有把“成功调用解码函数”等同于“所有字符串均正确”。这些选定 ID 也不代表整个 App 的全部字符串。

`CaptureIdPhotoActivity.onCreate()`、部分校验、状态处理和上传触发方法依然为 native。可以分析其可读辅助方法、回调和下游网络封装；不能据此宣称所有入口分支、活体条件或质量判断都已还原。

## 4. 二维码实际上如何进入采集流程

恢复出的扫码分派逻辑会从证件照链接中截取前缀后的内容，使用 UTF-8 URL 编码后重新构造 `chesicc://idphoto/...`，并显式启动 `CaptureIdPhotoActivity`。WebView 中也存在按相同 scheme／host 跳转的分支。

专用 Intent 辅助方法读取 `getPath().substring(1).trim()`，没有只取第一个路径片段。因此二维码参数里的 `/` 会作为整个参数的一部分保留；`+`、`.`、`=` 也不应被客户端随意替换。这个可读辅助方法没有自行解密二维码，后续业务请求把不透明参数作为 `issueId` 提交。

Activity 的 native 启动方法仍限制了完整调用链的证明范围。不过，扫码分派、路径提取、网络字段以及随后真实请求的结果相互吻合，足以支撑客户端所需的参数传递方式。

## 5. 上传协议是怎样恢复的

最有用的证据位于网络封装类、multipart 请求类、状态轮询器及 Activity 回调。它们显示，传输层接收一个 `File`，以 `image/jpeg` 写入 multipart 的 `file` 字段，并复制文件内容。

据此恢复的主要顺序为：

1. 调用公开设备初始化接口，取得业务公钥。
2. 调用 `/idphoto/v1/check`，提交 `issueId`，取得 `jwt` 和 `captureId`。
3. 调用 `/idphoto/v1/capture/osssign`，提交采集标识和背景处理选项。
4. 使用服务端返回的临时签名向 OSS 提交 JPEG multipart。
5. 调用 `/idphoto/v1/capture/ossrs`，回传 `stsId`、实际 ETag 等上传结果。
6. 调用 `/idphoto/v1/capture/checkst` 查询处理状态。
7. 需要完成 App 最终确认时，再调用 `/idphoto/v1/capture/confirm`。

业务请求使用 `did/v/k/d` 外层封装。`k` 包装随机对称密钥，`d` 包装内层 JSON，复现了 App 的 RSA、AES-CBC／PKCS7、Base64 和 URI 编码行为。后续请求将返回的 `jwt` 原样放入 `Authorization`，没有额外拼接 `Bearer`。

`check` 的 Java 请求封装不设置 `Authorization`，仅在非空时附加 `uid`；共享 CookieManager 有相应 cookie 时才添加 cookie。实际客户端成功路径没有要求用户输入账户密码，但这不构成所有采集任务均允许匿名使用的保证。

背景值是服务端识别的代码：`DEFAULT` 表示使用原图，`WHITE` 表示请求辅助替换白底。预先拍好的白底照片使用 `DEFAULT` 可以保留原图；它不是 RGB 值或 `#FFFFFF`。任务返回的 `bg` 选项仍应优先于本地默认选项。

OSS 响应中的 ETag从 XML 或响应头提取并去除双引号。回执接口的字段名为 `eTag`，与客户端内部结果中的 `etag` 大小写不同。上传到存储、后台接收回执、质量处理以及最终确认是不同阶段，不能只凭 HTTP 上传成功就宣称采集完成。

## 6. 不必先还原眨眼逻辑，才能理解文件上传

包内确有相机、人脸、姿态／眨眼等处理代码。它们证明官方客户端包含相应采集逻辑，不能单凭 SDK 或类名推断每个任务都要求相同的服务端凭证。

本次没有先实现这些动作，也没有修改 App 让某个检测返回成功。可读的网络封装及回调已暴露足够的文件上传协议，独立客户端可以读取已有 JPEG，申请任务对应的上传签名并回传存储结果。真实上传验证随后说明，当次服务端接受了这种输入路径并对那张照片给出 `PASS`。

这项观察没有证明 native 校验不存在，也没有证明任意非人像图片会通过，更没有把服务端失败结果替换成成功。

## 7. 实际上传与网页观察分别证明了什么

在用户提供新二维码和 JPEG 后，独立客户端真实完成了初始化、二维码校验、申请签名、OSS 上传及上传回执。OSS 返回 HTTP 201，后台随后返回：

```json
{
  "status": "QUALITY_CHECKING",
  "qualityStatus": "PASS",
  "confirmPhoto": 1
}
```

界面文案为“处理完成，待考生提交”。当次记录没有调用最终 `capture/confirm`，因此没有把上传成功或质量 `PASS` 写成“App 最终确认已完成”。

用户随后提供的报名平台截图中，新照片已经出现在“其他采集记录”，旁边可以选择“设为报名照片”；“当前报名照片”仍是旧记录。这说明照片已经进入可供网页选择的采集记录，同时也说明上传入库与报名网页选用照片是两个动作。该截图是用户提供的后续观察，不是客户端自动操作报名网页的结果。

本次任务还观察到二维码校验具有一次性状态影响。客户端因此在校验成功后保存会话，重试时复用已取得的任务凭证；不能把校验接口当作可以无限重复的无状态探测接口。

## 8. 当次 OSS policy 能说明的限制

另一次只申请签名、没有上传新文件的检查中，解码后的 policy 包含：

```json
["content-length-range", 1024, 1048576]
```

当次还出现了 bucket、临时安全令牌、签名版本、credential、日期、对象 key 和 `success_action_status` 相关约束。签名响应提供的字段包括：

```text
stsId, version, policy, xOssCredential, xOssDate, signature,
securityToken, objectKey, bucketName, host, expiration,
origin, successActionStatus, valid
```

这些是字段名，不是可复用的真实凭证。临时值和对象标识不进入公开文档。

该 policy 没有列出宽高、像素数或人像条件，但它只描述当次 OSS 上传约束；不能据此断言后续照片处理没有尺寸、解码、内容或质量检查。此范围也可能随任务及服务端版本改变。

## 证据范围

本次结论来自四个层次：APK 的静态结构、隔离环境取得的运行时 DEX、选定字符串的独立补解，以及用户授权后的单次真实上传和后续网页截图。公开仓库只保留实现与脱敏说明。

可以确认的是：该版本存在可复现的文件上传协议，而且本次提供的预拍 JPEG 已上传入库并获后台质量 `PASS`。尚不能推广的是：完整 native 实现、全部任务的准入条件、任意图片的接受情况，以及报名系统之后的审核结论。
