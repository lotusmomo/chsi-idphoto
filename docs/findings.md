# 分析结论与验证边界

本文区分 APK 中能直接观察的行为、独立客户端实际走通的流程，以及尚不能确认的服务端规则。具体请求结构见 [上传协议](protocol.md)。

## 研究对象

| 项目 | 值 |
| --- | --- |
| 应用 | CHSI Android |
| 版本 | 2.6.1 |
| APK 文件名 | `CHSI_APP_2.6.1.apk` |
| APK SHA-256 | `44b6585726ee3ecaebe28903a2e0c0bd78d2085277133de875b9f022d94e9967` |
| 主要入口 | `cn.com.chsi.chsiapp.base.idphoto.ui.CaptureIdPhotoActivity` |

APK 使用加固壳。运行时 DEX 导出后，JADX 恢复了业务类型、辅助类和部分回调；若干核心 Activity 方法仍声明为 native。导出 DEX 不等于把所有受保护方法恢复成可读 Java。

仓库提供独立客户端和分析文档，不分发原应用 APK、DEX、原生库、反编译源码、真实采集凭据或照片。

## 已确认的流程

扫码得到的 `chesicc://idphoto/...` 深链进入证件照采集模块。照片上传路径由设备初始化、二维码校验、OSS 授权、照片字节上传、回执提交、状态查询和照片确认组成。

独立 Python 客户端已在实际任务中使用 JPEG 文件完成上传流程。设备初始化、二维码校验、上传授权、OSS 接收、采集服务回执和状态处理均获得了实际响应；流程中的照片确认与报名网页的照片选用仍需要分别理解。

这证明服务端能够接收本次任务通过独立客户端发送的预拍 JPEG。它不能证明所有用户、所有任务、所有图片内容或未来版本都会得到相同结果。

### 一次性二维码

真实流程中，成功调用 `check` 后再次使用相同二维码，服务端返回已使用。后续阶段失败不会自动恢复二维码。

因此客户端在 `check` 后立即保存 JWT 和 `captureId`；重试时恢复同一任务。请求超时或成功响应尚未保存时，结果可能不确定，程序不会自动重发这类扫码请求。

### 背景选择

背景控件 `p156t3.a.j` 的默认选项为：

| 代码 | 含义 |
| --- | --- |
| `DEFAULT` | 使用原图 |
| `WHITE` | 请求辅助替换为白色背景，可能需要排队处理 |

已拍好所需白底的照片通常使用 `DEFAULT`，以保留上传图像。`WHITE` 表示额外的背景处理请求。具体可选值以当前任务 `check` 返回的 `bg` 数组为准。

## 照片格式、像素与文件大小

| 项目 | 已有证据 | 可以得到的结论 |
| --- | --- | --- |
| JPEG | Android 固定编码 JPEG，上传 MIME 为 `image/jpeg`；独立客户端已实际上传 JPEG | JPEG 是已验证格式 |
| PNG / HEIC / HEIF | 此采集路径未找到服务端允许列表，未做实际上传 | 支持情况未知，不能只改文件名或 MIME 就声称支持 |
| 480×640 像素 | `p124p3.l` 使用该裁剪配置，`p124p3.b.a` 创建对应尺寸的输出 Bitmap | 是客户端成片尺寸，不能据此认定为服务器最大尺寸 |
| 100–300 KiB | `p124p3.i.b` 的压缩参数为 100、300，并乘以 1024 | 是客户端压缩目标，不是可靠硬限制 |
| 1 KiB–1 MiB | 已观察到的服务端 OSS policy 包含对应 `content-length-range` | 是该次上传授权的文件长度范围，不是全局照片业务规则 |
| 最大宽、高、像素总量 | 未在该路径恢复的服务端约束中获得明确值，未做边界上传 | 仍未知 |

### 为什么 100–300 KiB 不是硬限制

`p124p3.i.b` 从 JPEG 质量 95 开始，每次降低 5，尝试把文件压到 300 KiB 内。质量降至约 40 后仍超出目标，也没有抛出超限错误，而是继续写文件。

文件小于 100 KiB 时，它只是重新使用质量 95 编码。重编码后仍可能低于 100 KiB，也可能再次超过 300 KiB。这个方法没有保证最终文件处于某个严格区间。

### OSS policy 的范围

已验证任务的策略还使用 `eq` 固定对象键，意味着授权只允许写入服务端指定的那个对象，不能改成自选文件路径。策略包含过期时间和临时凭据约束。

即使满足 OSS 的大小和对象键条件，照片仍可能在后续业务处理中因尺寸、人像质量、背景或其他任务规则被拒绝。对象存储接收成功不能代替照片审核结果。

## 本地检测与尚未恢复的门控

可读代码表明，官方客户端在相机保存回调后执行：

- 单人脸检测与姿态检查。
- 构图裁剪和 JPEG 编码。
- 背景亮度、色彩和白底判断。
- 一套连续帧眨眼和人脸连续性状态机。

`p172v3.a` 中存在睁眼、闭眼、重新睁眼及人脸变化后的重置逻辑，Activity 也实例化了该类。但可读 Java 中没有恢复从帧处理到该实例 `w` 方法的完整调用边；帧入口、检测桥和拍摄门控仍包含 native 方法。

因此可以确认模块中有眨眼实现，不能仅凭这些成员和提示语完整证明每一条入口的实际门控，更不能据此断定后台存在或不存在活体票据。

本工具直接发送用户提供的 JPEG，不运行 Android 本地检测，不伪造眨眼数据、相机事件或服务端审核通过结果。照片是否满足后续规则，以服务端响应为准。

### 相册入口的证据

没有在已恢复的 `CaptureIdPhotoActivity` Java 中找到证件照相册选择器。另一个 `CustomScannerActivity.photoAlbum` 方法属于二维码扫描模块，不能据此认定官方证件照页面允许从相册选照片。

## 上传、确认与报名照片选用

客户端将这些状态分别记录：

1. **OSS 上传完成**：存储服务接收文件，返回实际 ETag。
2. **回执被采集服务接受**：`capture/ossrs` 成功，并返回有效处理参数。
3. **服务器返回处理状态**：包括 `qualityStatus`、提示和允许的下一步操作。
4. **采集照片已确认**：用户请求确认，且 `capture/confirm` 返回成功。
5. **报名网页选用了该照片**：网页中的另一项业务操作。

其中任意一步都不能自动推导后续步骤完成。`QUALITY_CHECKING` 是状态交接点，不能单独解释为审核通过。客户端也不把不认识的状态自动当成成功。

`capture/confirm` 与网页“用作报名照片”含义不同。确认采集照片后，报名页面仍可能要求用户预览、选用和提交。本仓库没有实现报名网页的选用接口，也没有将采集确认描述为报名已完成。

## 已做验证与未做验证

| 类别 | 范围 |
| --- | --- |
| APK 静态与运行时分析 | Manifest 深链、运行时 DEX、JADX 类和方法、受保护字符串、加密与上传辅助类 |
| 离线模拟 | 请求加解密、multipart 文件字节、回执和状态分支、故障后的检查点恢复 |
| 实际服务 | 公开设备初始化、实际二维码任务的 JPEG 上传链及对应服务响应 |
| 未做的边界测试 | 最大像素、超大文件、最小文件、非 JPEG、批量任务和其他账号/任务规则 |
| 未恢复的实现 | 部分 Activity native 方法、全部本地检测门控、服务端内部审核逻辑、报名网页选用接口 |

离线模拟只能验证独立实现内部的编解码和控制流，不能代替线上协议兼容性。一次实际成功也不能建立图片格式和大小的完整允许集合。

本文没有把网站未公开的规则补写成事实，也没有通过反复消费二维码或边界上传来探测限制。服务端字段和策略变化时，应保留原始状态含义并报告失败或未知结果。
